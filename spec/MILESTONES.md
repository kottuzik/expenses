# MILESTONES – מערכת לניהול הוצאות הבית

מסמך זה מגדיר את סדר הפיתוח על בסיס `PRD.md`, `ARCHITECTURE.md` ו-`DESIGN.md`. כל Milestone הוא תוצר עובד הניתן להדגמה ולאישור. דרישות ה-PRD גוברות על רכיבים חזותיים סותרים: **אין הרשמה, חשבונות אישיים או פרופילים נפרדים**, גם אם הופיעו בתמונות. ממשק המוצר בעברית וב-RTL.

## Development Execution Rules – הוראות מחייבות ל-AI המפתח

1. יש לממש את ה-Milestones **לפי הסדר** המוגדר כאן, ללא דילוגים.
2. בכל Milestone יש לממש את היכולת מקצה לקצה, לרבות UI, API, Database, הרשאות ובדיקות רלוונטיות; אין להסתפק ב-Mockup או בנתונים מדומים כאשר נדרש תוצר עובד.
3. **בסיום כל Milestone יש לעצור**, להציג למשתמש את התוצר, את דרך הבדיקה ואת תוצאות הבדיקות ביחס לכל סעיף ב-Definition of Done; לציין במפורש בדיקות שנכשלו או לא בוצעו.
4. **אין להתחיל את ה-Milestone הבא ללא אישור מפורש של המשתמש.** אישור של קוד או פריסה אינו משתמע מאישור של שלב קודם.
5. שינויי Database Schema ייכתבו כ-Database Migrations ב-Git, ויורצו וייבדקו תחילה **רק על Supabase Development**. אין להריץ Migration על Production במסגרת Milestones של פיתוח. העברה ל-Production מתבצעת רק בנוהל המוגדר ב-Milestone הפריסה, לאחר אישור מפורש.
6. יש לשמור על הפרדה מלאה בין Development ל-Production: אין להעתיק נתונים אמיתיים ל-Development, אין להכניס Secrets ל-Git ואין להשתמש בפרטי Production במחשב המקומי.
7. יש להשתמש ב-Technology Stack ובכללי האבטחה, ה-RTL והעיצוב שהוגדרו במסמכי הפרויקט, בלי להוסיף פיצ'רים שלא אושרו.
8. כל מסך נבנה כבר ב-Milestone שלו גם למובייל וגם ל-Desktop, לפי ״פריסת Desktop ו-Tablet״ ב-`DESIGN.md`, ועומד בכללי הנגישות שם.
9. כל שירות חיצוני מוקם רק ב-Milestone שבו הוא נדרש לראשונה: Supabase Development ב-1, Gmail SMTP ב-6, Cloudflare R2 (Dev) ב-7, וכל סביבת Production (Supabase, R2, Vercel) ב-8. הקמת חשבונות נעשית על ידי המשתמש, בהדרכה צעד אחר צעד.
10. הבדיקות רצות רק מול Supabase Development, עם נתוני בדיקה מסומנים שמנוקים בסיום, ועם שעון ניתן להזזה – לפי סעיף 9 ב-`ARCHITECTURE.md`.

## Milestone 1 – הקמת מערכת מאובטחת וכניסה משפחתית ✅

**מטרה:** להקים אפליקציה ניתנת להרצה עם גישה פרטית באמצעות סיסמה משפחתית אחת, ללא הרשמה.

**מה יש לממש:**
- פרויקט Next.js + React + TypeScript עם CSS Modules, מבנה RTL, גופנים (Inter + Heebo), משתני צבע ועיצוב בסיסי לפי `DESIGN.md`, ומעטפת ניווט רספונסיבית: Bottom Navigation במובייל וניווט צד ב-Desktop. היעדים שעדיין לא נבנו מוצגים כ״בקרוב״.
- **בהדרכה צעד אחר צעד למשתמש:** יצירת **פרויקט Supabase Development אחד בלבד** בענן, ללא Docker או Supabase מקומי:
  - יצירת משתמש Auth טכני יחיד.
  - חסימת Signup ציבורי.
  - אורך סיסמה מינימלי 8.
  - תוקף JWT של 10 דקות.

  Production, R2 ו-Vercel **אינם** מוקמים בשלב זה.
- קובץ `.env.example` עם שמות המשתנים בלבד, והעתקתו ל-`.env` שאותו המשתמש ממלא בפרטי **Development בלבד** (לפי `CLAUDE.md`).
- Migration ראשון ב-Development: `app_state`, `change_signals`, `login_attempts` וכללי RLS הדרושים.
- מסך התחברות בסיסמה בלבד דרך Supabase Auth (`@supabase/ssr`), בדיקת Session בשרת מול `auth.sessions` כולל מגבלת 30 יום, Logout, Rate limiting לניסיונות כניסה והגנת CSRF; מסך בית מוגן ראשוני ללא נתוני הוצאות.
- תשתית בדיקות Vitest/React Testing Library/Playwright, פונקציית `now()` ניתנת להזזה, סקריפט `npm run test:reset` ותיעוד קצר להרצה מול Development בענן.
- ה-repo ב-GitHub נוצר על ידי המשתמש ומחובר בדחיפה הראשונה, לפי `CLAUDE.md`.

**תוצר מצופה:** ניתן להפעיל את האפליקציה מקומית, להתחבר עם הסיסמה המשפחתית של סביבת Development, להיכנס לאזור מוגן ולהתנתק.

**Definition of Done:**
- פרויקט Supabase Development קיים; סביבת הפיתוח המקומית מחוברת רק אליו; אין Secrets ב-Git (`.env` מוחרג ב-`.gitignore`, `.env.example` ללא ערכים).
- Migration התשתית הורץ בהצלחה ב-Development; RLS והרשאות נבדקו; אין Signup ציבורי.
- גישה לנתונים/Routes מוגנים ללא Session תקף נחסמת בשרת; התחברות ו-Logout עובדים; Session שגילו מעל 30 יום נדחה (נבדק עם שעון מוזז); ניסיונות כניסה כושלים חוזרים נחסמים זמנית.
- `npm run build` ובדיקות כניסה/הרשאות עוברות; מסך הכניסה בעברית ו-RTL, ללא מסך הרשמה ושדה Email; מעטפת הניווט תקינה במובייל וב-Desktop.
- המשתמש יכול לבצע בעצמו את הוראות ההפעלה ולקבל תוצאה עובדת.

## Milestone 2 – ניהול קטגוריות והוצאות מקצה לקצה ✅

**מטרה:** לאפשר תיעוד ותחזוקה אמיתיים של הוצאות הבית במסד הנתונים.

**מה יש לממש:**
- Migrations ל-`categories` ו-`expenses`, אילוצים ואינדקסים; יצירת קטגוריות התחלתיות: מזון, ביגוד, רשויות, פנאי, אחר.
- ניהול קטגוריות (נגיש ממסך ״עוד״): הוספה, שינוי שם וצבע מתוך פלטת 12 הצבעים, מחיקה והעברת הוצאות לקטגוריה חלופית בעסקה אחת; מניעת שמות כפולים; חסימת מחיקת הקטגוריה האחרונה; הצגת קטגוריות ריקות. שינוי שם/צבע מתעדכן גם בהוצאות עבר.
- מסך הוצאות, טופס הוספה ועריכה (Dialog ב-Desktop), שכפול הוצאה לטופס חדש, ולידציה בלקוח ובשרת לפי ה-PRD (סכום עד ₪1,000,000, תאריך מ-01.01.2000 ועד היום, תיאור עד 200 תווים); אזהרת יציאה משינויים שלא נשמרו.
- רשימת הוצאות פעילות עם 20 פריטים בעמוד, תצוגת שורה לפי ה-PRD (תיאור, או שם קטגוריה כשאין תיאור), סינון לפי טווח תאריכים וקטגוריה אחת, ומיון לפי תאריך/סכום בשני הכיוונים.
- API מאומת, סכומים מדויקים ב-PostgreSQL ותאריכים לפי `Asia/Jerusalem`; מניעת פעולות שינוי כאשר אין חיבור.

**תוצר מצופה:** משפחה יכולה לנהל קטגוריות ולהוסיף, לערוך, לשכפל ולמצוא הוצאות שנשמרות בענן Development.

**Definition of Done:**
- כל Migrations של השלב הורצו ונבדקו ב-Development בלבד; נתוני קטגוריות התחלתיות אינם נוצרים פעמיים.
- סכום לא חיובי או מעל ₪1,000,000, יותר משתי ספרות עשרוניות, תאריך עתידי או לפני 01.01.2000, קטגוריה חסרה ותיאור ארוך מ-200 תווים נדחים גם בשרת; תיאור נשאר אופציונלי.
- לא ניתן למחוק את הקטגוריה האחרונה; צבע קטגוריה מחוץ לפלטה נדחה בשרת.
- ניתן להוסיף, לערוך ולשכפל הוצאה; יציאה עם שינויים לא שמורים דורשת בחירה מפורשת.
- סינון, מיון ו-Pagination של 20 עובדים מול נתוני DB, לרבות מעבר עמודים.
- שינוי קטגוריה משפיע על כל ההוצאות המשויכות; מחיקת קטגוריה עם הוצאות מחייבת חלופה ומעבירה את כל ההוצאות באופן עקבי.
- משתמש לא מאומת אינו יכול לקרוא או לשנות הוצאות וקטגוריות; בדיקות CRUD ו-Constraints עוברות.

## Milestone 3 – Dashboard, סיכומים והשוואת תקופות

**מטרה:** להפוך את נתוני ההוצאות לתמונת מצב ולהשוואה שימושית.

**מה יש לממש:**
- Dashboard עם סך הוצאות החודש הנוכחי, Donut/Pie לפי קטגוריות, חמש ההוצאות האחרונות (לפי תאריך הוצאה ואז מועד הזנה) וכפתור הוספה.
- מסך גרפים וסיכומים (יעד ״סיכומים״ בניווט הראשי) לתקופות יום, שבוע (ראשון–שבת), חודש, שנה וטווח מותאם, עם חצי מעבר לתקופה קודמת/הבאה; סכום כולל ופירוט קטגוריות. ללא גרף ״לאורך זמן״.
- השוואה ידנית בין שתי תקופות, כש״תקופה א׳״ היא הבסיס: סכומים, הפרש כספי ואחוזי של ב׳ ביחס לא׳, השוואה לפי קטגוריות ו-Bar Chart.
- חישובים ב-Database/API ללא הוצאות מחוקות; פורמט ₪, RTL, מצבים ריקים וייצוג טקסטואלי נגיש לנתוני גרפים.

**תוצר מצופה:** ניתן לצפות במצב ההוצאות הנוכחי ולבחור תקופות לצפייה ולהשוואה על בסיס נתונים אמיתיים.

**Definition of Done:**
- Dashboard מציג נתוני חודש נוכחי וחמש הוצאות אחרונות בהתאם לנתוני Development.
- סכומי תקופות ופירוט קטגוריות תואמים לסכומי ההוצאות הפעילות; קטגוריות ללא הוצאות אינן מוצגות בגרפי סיכום.
- שבוע נמדד מיום ראשון עד שבת; טווח מותאם כולל את שני תאריכי הקצה.
- בהשוואה מוצגות כל הקטגוריות עם הוצאות לפחות באחת התקופות, ו-₪0 בצד שבו אין הוצאות.
- כשסכום תקופת הבסיס הוא אפס מוצג הפרש כספי והטקסט **״אין נתון להשוואה״**, ללא חלוקה באפס.
- בדיקות חישוב, מצבים ריקים ותצוגת Mobile/Desktop עוברות; אין Migration שלא הורץ ב-Development.

## Milestone 4 – סל מחזור ועריכה מקבילה בין מכשירים

**מטרה:** לאפשר מחיקה בטוחה ועבודה עקבית של בני הבית מכמה מכשירים.

**מה יש לממש:**
- העברה לסל מחזור (`deleted_at`), מסך סל מחזור, שחזור ומחיקה לצמיתות; הצגת תאריך מחיקה, ימים שנותרו ואזהרה בשבעת הימים האחרונים.
- מחיקה אוטומטית לאחר 30 יום באמצעות Job מאובטח ו-Idempotent, עם בדיקת תוקף גם ב-API אם Job התעכב.
- Supabase Realtime לרענון הוצאות, קטגוריות, Dashboard וגרפים במכשירים מחוברים; Refetch לאחר חיבור מחדש.
- `version`/Optimistic Concurrency: התנגשות עריכת אותה הוצאה עם אפשרות לטעון את העדכון או לדרוס במפורש; חסימת שמירה לאחר מחיקת הוצאה במכשיר אחר; קטגוריה שנמחקה בזמן עריכה מחייבת בחירה מחדש, ושינוי שם/צבע מתעדכן בלי לחסום.
- Realtime מאזין לטבלת `change_signals` בלבד (טריגרים מעלים `data_epoch`).

**תוצר מצופה:** מחיקה ניתנת לשחזור בזמן המותר, והנתונים מתעדכנים בין מכשירים ללא דריסה שקטה של שינויים.

**Definition of Done:**
- כל שינוי Schema הורץ ב-Development בלבד; בדיקות DB מאמתות מחיקה רכה, שחזור ומחיקה לצמיתות.
- הוצאה בסל המחזור אינה נכללת ברשימות ובסיכומים; שחזור מחזיר אותה; מחיקה לצמיתות אינה ניתנת לביטול דרך הסל.
- חלוף 30 יום מתאריך המחיקה המקורי גורם למחיקה לצמיתות; אזהרה מופיעה בשבעת הימים האחרונים; Job ניתן להרצה חוזרת ללא נזק.
- שני מכשירים מחוברים רואים שינויי נתונים ללא רענון ידני; חיבור מחדש מרענן את הנתונים.
- התנגשות עריכה אינה דורסת אוטומטית; מחיקה מקבילה חוסמת שמירה; קטגוריה שנמחקה מחייבת בחירה מחדש; שינוי שם קטגוריה אינו חוסם שמירה.
- העברה לסל מחזור מתבצעת ללא חלון אישור, עם הודעת הצלחה.
- בדיקות שני מכשירים, התנגשויות ו-Job עוברות.

## Milestone 5 – ייבוא וייצוא CSV

**מטרה:** לאפשר העברת הוצאות למערכת וממנה באופן מבוקר, בלי לאבד נתונים תקינים.

**מה יש לממש:**
- כפתור ייצוא CSV במסך ההוצאות: כלל ההוצאות הפעילות או ההוצאות לפי הסינון הנוכחי; UTF-8 עם BOM וכותרות בעברית.
- מסך ייבוא (נגיש ממסך ״עוד״) עם בחירת קובץ עד 2MB, כותרות בעברית או באנגלית, בדיקת מבנה ושורות לפני שמירה, תיקון שורות לא תקינות בממשק, זיהוי כפילויות אפשריות בתוך הקובץ ומול הוצאות קיימות, והחלטה מפורשת אילו לייבא.
- טיפול בקטגוריה לא מוכרת: יצירה או שיוך לקטגוריה קיימת.
- שמירת שורות תקינות גם במקרה של כישלון חלקי, הצגת שורות שנכשלו וניסיון חוזר רק עבורן; הגנות על קובצי קלט/פלט.

**תוצר מצופה:** ניתן לייצא הוצאות ולייבא קובץ עם בדיקה ותיקון, תוך שליטה בכפילויות ובשגיאות.

**Definition of Done:**
- CSV מיוצא מכיל רק הוצאות פעילות, בהתאם לבחירת כל הנתונים או הסינון; הקובץ נפתח ב-Excel עם עברית תקינה; ייבוא חוזר של קובץ שיוצא מהמערכת עובד, וכל שורותיו מסומנות ככפילויות אפשריות.
- קובץ עם שורות לא תקינות אינו נשמר ללא תיקון או החלטת משתמש; כפילויות אפשריות מסומנות לבחירה.
- קטגוריות לא מוכרות מטופלות רק לאחר בחירה מפורשת; כל רשומה מיובאת עומדת באותן ולידציות כמו הוצאה ידנית.
- כישלון חלקי משאיר רשומות שהצליחו, ומנגנון Retry אינו מכפיל אותן.
- בדיקות קבצים פגומים, ניסיון ייבוא חוזר ו-CSV formula injection עוברות; כל Migration נדרש הורץ ב-Development בלבד.

## Milestone 6 – הגדרות גישה, שחזור סיסמה ו-PWA Offline

**מטרה:** להשלים שימוש פרטי רציף במכשירים אישיים ובטיחות של הגישה למידע.

**מה יש לממש:**
- מסך ״עוד״ המלא, ובו שינוי סיסמה לאחר אימות הסיסמה הנוכחית; ביטול Sessions בכל המכשירים (`signOut` גלובלי והעלאת `auth_epoch`), כולל המכשיר המבצע.
- שחזור סיסמה בקישור Email, ללא שדה כתובת ועם הצגת הכתובת במיסוך חלקי; שינוי כתובת Email לשחזור לאחר אימות סיסמה ואישור הכתובת החדשה בלבד. **בהדרכה צעד אחר צעד למשתמש:** הגדרת Gmail SMTP (אימות דו-שלבי וסיסמת אפליקציה) ב-Supabase Development; תוקף קישור של שעה.
- Web App Manifest ו-Service Worker להתקנת PWA; IndexedDB/Cache מבוקר לצפייה **בנתונים שכבר נטענו** במצב Offline, ללא פעולות כתיבה Offline.
- מחיקת/בידוד נתוני Cache בעת Logout וביטול Sessions, טיפול בפקיעת התחברות לאחר חיבור מחדש.

**תוצר מצופה:** ניתן לשנות או לשחזר את הסיסמה, לנהל Email שחזור, להתקין את האפליקציה ולצפות במידע שכבר נטען ללא חיבור.

**Definition of Done:**
- שינוי סיסמה דורש סיסמה נוכחית, מבטל את כל ה-Sessions וגורם לדרישת התחברות מחדש בכל המכשירים; גם מכשיר Offline נחסם כאשר הוא חוזר לרשת.
- Email שחזור נשלח דרך תצורת Development, קישור האיפוס פועל, ושינוי Email נכנס לתוקף רק לאחר אישור הכתובת החדשה.
- ניתן להתקין PWA בדפדפן נתמך; מידע שכבר נטען נגיש Offline, אך הוספה/עריכה/מחיקה/ייבוא נחסמים באופן ברור.
- לאחר Logout לא ניתן לראות מידע משפחתי מתוך Cache ללא אימות; אין Secrets ב-Client או ב-Git.
- בדיקות Authentication, Email, Offline ו-Reconnect עוברות; Migrations נדרשים הורצו ב-Development בלבד.

## Milestone 7 – גיבויים חודשיים ושחזור מלא ובטוח

**מטרה:** להגן על נתוני הבית באמצעות Snapshots ושחזור מלא, עקבי וניתן לבדיקה.

**מה יש לממש:**
- **בהדרכה צעד אחר צעד למשתמש:** יצירת חשבון Cloudflare ו-R2 bucket פרטי ל-Development בלבד, ומפתחות גישה מוגבלים שהמשתמש מוסיף ל-`.env`.
- Snapshots חודשיים עקביים של קטגוריות והוצאות, כולל סל מחזור ותאריך מחיקה מקורי; אחסון פרטי ב-Cloudflare R2 ושמירת 12 הגיבויים החודשיים האחרונים (`UNIQUE (kind, period)`).
- Job מתוזמן, מוגן ו-Idempotent ליצירת גיבוי ולניקוי גיבויי safety שפג תוקפם.
- מסך גיבויים ושחזור: רשימת גיבויים לפי תאריך, כולל גיבויי בטיחות מסומנים, בחירת Snapshot ואישור מפורש לפני החלפה מלאה. ללא כפתור גיבוי ידני.
- נעילת כתיבות גלובלית בזמן שחזור, עם זמן תפוגה (`maintenance_until`) ושחרור אוטומטי לאחר קריסה; יצירת Snapshot safety לפני שינוי נתונים ושמירתו 30 יום; כישלון safety מבטל את השחזור. תיעוד כל שחזור בטבלת `restores`.
- שחזור בעסקת DB אטומית עם Rollback במקרה כישלון, אימות שלמות Snapshot, המרת Snapshot ממבנה ישן (`schema_version`) ורענון כל המכשירים לאחר הצלחה; שמירת שעון המחיקה המקורי של הוצאות בסל.
- בדיקת זמן ריצה מול נתוני בדיקה בנפח 20,000 הוצאות; אין להציג שחזור כתקין בלי בדיקת End-to-End.

**תוצר מצופה:** המשתמש יכול לבחור גיבוי ולשחזר מצב מלא, בלי לסכן את המצב הקודם או לאפשר שינויים מקבילים בזמן הפעולה.

**Definition of Done:**
- Migrations של קטלוג הגיבויים/נעילת תחזוקה הורצו ונבדקו ב-Development בלבד.
- Snapshot חודשי נוצר ונשמר ב-R2 פרטי עם checksum; ריצה חוזרת אינה יוצרת כפילויות; נשמרים לכל היותר 12 גיבויים חודשיים תקינים.
- שחזור מוצלח מחליף את ההוצאות והקטגוריות באופן מלא; הוצאות מחוקות שומרות `deleted_at` המקורי ואת מדיניות 30 הימים.
- לפני כל שחזור נוצר safety backup; כישלון ביצירתו מבטל את השחזור ללא שינוי נתונים; safety נשמר 30 יום ונמחק לאחר מכן.
- כתיבה מכל מכשיר חסומה בזמן שחזור; כישלון בשחזור אינו מותיר נתונים חלקיים; לאחר הצלחה כל המכשירים מתעדכנים.
- ניתן לשחזר מגיבוי בטיחות (ביטול שחזור); נעילה שפג תוקפה משתחררת והשחזור מסומן `failed`; Snapshot ממבנה קודם משוחזר תקין.
- בדיקות שחזור מול 20,000 הוצאות, כשל באמצע תהליך, Rollback, נעילה ו-checksum עוברות; אם זמן הריצה חורג ממגבלת Vercel – עוצרים ומחליטים עם המשתמש על פתרון חלופי לפני אישור השלב.

## Milestone 8 – פריסת Production ואימות המוצר השלם

**מטרה:** לפרסם את המערכת הפרטית ולהבטיח שהגרסה החיה תואמת לגרסה שנבדקה ב-Development.

**מה יש לממש:**
- **בהדרכה צעד אחר צעד למשתמש:**
  - יצירת פרויקט Supabase Production.
  - יצירת R2 bucket פרטי ל-Production.
  - יצירת **פרויקט Vercel אחד** מחובר ל-GitHub, עם משתני סביבה נפרדים: היקף Preview מפנה ל-Supabase Dev, והיקף Production ל-Supabase Prod.
- השלמת תצורה נפרדת ב-Production: Supabase Auth ומשתמש טכני יחיד (חסימת Signup, סיסמה מינימלית, תוקף JWT ו-OTP), RLS/Realtime, Gmail SMTP, Cron, Redirect URLs; ללא העתקת נתוני Development.
- **נוהל אישור Production מחייב:**
  - Claude מכין ומציג למשתמש את רשימת ה-Migrations שנבדקו ב-Development ואת השפעתם, ודוחף אותם לענף נפרד.
  - רק לאחר אישור מפורש, **המשתמש עצמו** מפעיל ב-GitHub את ה-workflow הידני `migrate-production` (כפתור ״Run workflow״), עם credentials של Production השמורים כ-Repository Secrets. ה-workflow מריץ `db push --dry-run` ואז `db push` על Production.
  - אם הבדיקות נכשלות – אין פריסה.
  - לא משתמשים ב-Environment Approval, שאינו זמין ל-repo פרטי בתוכנית החינמית.
- סדר פריסה: **Production DB Migrations → בדיקת תקינות → Push ל-`main` → Vercel Production Deployment**. אין להריץ Migrations של Production אוטומטית בכל Push. שינויים שוברי תאימות דורשים תהליך תואם-לאחור לפני הפריסה.
- **מניעת השהיה של Supabase Free:** לוודא בתיעוד הרשמי שהשאילתה היומית של ה-Cron נחשבת פעילות. אם לא – להציג למשתמש את הבחירה בין Pro לבין קבלת הסיכון, ולתעד הוראות הפעלה מחדש.
- בדיקות End-to-End של מסכי המוצר, אבטחה, Mobile/Desktop, RTL, PWA, Realtime, CSV, סל מחזור, Email וגיבוי/שחזור ב-Production עם נתוני בדיקה מבוקרים, ללא פגיעה בנתונים אמיתיים.

**תוצר מצופה:** אפליקציית Production פרטית, נגישה בכתובת האתר, עם Deployment אוטומטי של קוד לאחר אישור שינויי Database נדרשים.

**Definition of Done:**
- כל Migrations הנדרשים נבדקו קודם ב-Development, אושרו במפורש על ידי המשתמש, הורצו בהצלחה ב-Production **לפני** פריסת גרסת הקוד התלויה בהם; קיימת עדות לתוצאות ה-Pipeline.
- פריסת Production דרך GitHub → Vercel עובדת; משתני Preview מפנים ל-Development בלבד; אין Secrets או נתונים אמיתיים ב-Repository או בסביבת הפיתוח המקומית.
- התקבלה והתועדה החלטה לגבי השהיית Supabase Free (פעילות Cron מספיקה, Pro או קבלת סיכון).
- התחברות בסיסמה משותפת, שינוי/שחזור סיסמה, CRUD, Dashboard, דוחות, Realtime, CSV, סל מחזור, PWA וגיבוי/שחזור פועלים בסביבה החיה.
- גיבויים נשמרים ב-bucket פרטי ונבדק שחזור מבוקר; Cron, SMTP ו-RLS נבדקו בהגדרות Production.
- תוצאות בדיקות Desktop/Mobile, RTL, הרשאות, Offline ותרחישי כשל מתועדות; כל תקלה חוסמת משמעותית נפתרה לפני אישור סופי.
